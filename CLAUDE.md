## 2. Project mission

Build a research-grade Python simulator that compares two supply-chain disruption-response policies:

1. a transparent classical heuristic;
2. a bounded LLM-enabled decision agent.

The project must answer:

> Under identical disrupted supply-chain conditions and operational constraints, can a bounded LLM-enabled policy produce valid shipment-level decisions that reduce the incremental cost of disruption more effectively and robustly than a classical heuristic?

The system must compare policies, not give one policy a more favorable world.

## 3. Version 1 scope

### 3.1 What Version 1 is

Version 1 is a discrete-time, single-product, transportation-and-inventory simulator.

It represents:

- a directed logistics network;
- suppliers, ports, hubs, and one demand destination;
- shipments released according to a fixed replenishment schedule;
- inventory at the destination;
- stochastic daily demand;
- ordinary transport delays;
- temporary network disruptions;
- shipment-level decisions;
- route changes and emergency transport;
- service and cost consequences;
- paired disrupted and undisrupted experiments.

Time advances in whole days.

### 3.2 What policies control

Policies may decide only what to do with an existing shipment that is waiting at a node and requires intervention.

The shared actions are:

- `WAIT`;
- `REROUTE`;
- `EXPEDITE`;
- `ABSTAIN`.

Policies do not create supply, change customer demand, modify the network, or bypass validation.

### 3.3 Explicit non-goals

Version 1 does not include:

- supplier selection;
- procurement decisions;
- production planning;
- manufacturing bills of material;
- multiple products;
- product substitution;
- shipment splitting;
- partial expedition;
- joint optimization across multiple shipments;
- new order creation by a policy;
- dynamic pricing;
- vehicle-level scheduling;
- fleet routing;
- carbon-emission objectives;
- human approval workflows;
- free-form news interpretation;
- uncertain disruption duration;
- delayed or asymmetric information;
- reinforcement learning;
- policy training or fine-tuning;
- a database;
- a web application;
- distributed execution;
- microservices;
- asynchronous simulation;
- real-time operation.

These may be studied later, but they must not appear in Version 1 unless Yassine explicitly changes the contract.

## 4. Engineering philosophy

### 4.1 Simplicity first

Always choose the simplest correct implementation.

Prefer:

- one clear function over a framework;
- a dataclass over an elaborate object hierarchy;
- an explicit loop over hidden orchestration;
- standard-library serialization over a database;
- deterministic local calculations over an external service;
- a small number of dependencies;
- direct names matching the domain.

Do not write code for hypothetical future use.

### 4.2 Minimal code

Every class, function, file, dependency, configuration field, and abstraction must solve a current Version 1 requirement.

Do not add:

- generic repositories;
- service locators;
- dependency-injection frameworks;
- plugin systems;
- event buses;
- abstract factories;
- generic workflow engines;
- catch-all utility modules;
- compatibility layers;
- speculative extension points;
- unused interfaces;
- placeholder modules.

### 4.3 Separation of concerns

Protect this separation:

```text
Simulation physics
≠
Decision policy
≠
Experiment orchestration
≠
External LLM integration
≠
Input/output
```

- Simulation physics determines what happens after a validated action.
- A policy chooses an action from a read-only observation.
- Experiment orchestration creates fair, paired runs.
- The LLM integration communicates with the external provider.
- Input/output loads configuration and saves results.

### 4.4 Surgical changes

For every task:

- inspect the current state before editing;
- identify the smallest required file set;
- modify only the requested responsibility;
- add only directly related tests;
- preserve unrelated behavior;
- report unrelated problems instead of fixing them;
- never reformat or rewrite an entire file for a local change.

### 4.5 Goal-driven execution

Before coding, define:

- the goal;
- the allowed scope;
- what “done” means;
- the verification commands;
- any risk to scientific validity.

After coding, verify the completion condition before moving forward.

### 4.6 Scientific validity before convenience

If a convenience feature threatens fairness, reproducibility, or auditability, do not implement it.

Examples:

- never sample separate demand for each policy;
- never let the LLM call a routing function unavailable to the heuristic calculations;
- never silently repair an invalid LLM route;
- never skip a failed replication and average the rest;
- never change a cost coefficient for only one branch;
- never execute a policy against a mutated state from a prior branch.

## 5. Formal model

## 5.1 Base network

The normal supply chain is a directed graph:

$$
\bar{G} = (V, E)
$$

where:

- $\bar{G}$ is the immutable base network;
- $V$ is the set of nodes;
- $E$ is the set of directed transport edges.

An edge $(i, j)$ permits movement from node $i$ to node $j$. It does not imply movement from $j$ to $i$.

## 5.2 Node meaning

Each node represents one location.

Supported node types are exactly:

```text
SUPPLIER
PORT
HUB
PLANT
CUSTOMER
```

Version 1 uses `PLANT` as the final demand destination.

Each node has:

| Field | Type | Meaning |
|---|---:|---|
| `node_id` | `str` | Unique stable identifier |
| `name` | `str` | Human-readable name |
| `node_type` | enum | Operational role |
| `latitude` | `float \| None` | Optional reporting coordinate |
| `longitude` | `float \| None` | Optional reporting coordinate |
| `storage_capacity` | `int` | Maximum quantity physically waiting or stored at the node |
| `processing_capacity` | `int` | Maximum quantity allowed to depart from the node per day |
| `source_capacity` | `int` | Maximum quantity a supplier may release per day |

All capacities are non-negative integers.

For non-supplier nodes, `source_capacity` must be `0`.

## 5.3 Edge meaning

Each edge represents one transport lane.

Supported modes are exactly:

```text
ROAD
RAIL
SEA
AIR
```

Each edge has:

| Field | Type | Meaning |
|---|---:|---|
| `edge_id` | `str` | Unique stable identifier |
| `origin_node_id` | `str` | Start node |
| `destination_node_id` | `str` | End node |
| `mode` | enum | Transport mode |
| `distance_km` | `float` | Reporting distance |
| `base_lead_time_days` | `int` | Normal traversal time |
| `daily_capacity` | `int` | Maximum quantity entering the edge per day |
| `unit_transport_cost` | `float` | Cost per unit entering the edge |
| `reliability` | `float` | Probability of receiving no ordinary extra delay |
| `emergency` | `bool` | Whether the edge is an emergency option |

Validation rules:

- lead time must be at least `1`;
- capacity must be non-negative;
- cost must be non-negative;
- reliability must satisfy \(0 \leq reliability \leq 1\);
- origin and destination must exist;
- origin and destination must differ;
- duplicate `edge_id` values are forbidden;
- two nodes may have multiple lanes only if every lane has a distinct `edge_id`.

## 5.4 Current operational network

The operational graph on day $t$ is:

$$
G_t = \Phi(\bar{G}, Z_t)
$$

$G_t$ consists of the immutable base definitions plus temporary operational states.

Node operational state:

```text
available
processing_capacity_multiplier
```

Edge operational state:

```text
available
capacity_multiplier
lead_time_multiplier
cost_multiplier
```

All multipliers default to `1.0`.

The effective edge values on day $t$ are:

$$
\text{capacity}_{e,t} = \left\lfloor \text{base\_capacity}_e \times \text{capacity\_multiplier}_{e,t} \right\rfloor
$$

$$
\text{lead\_time}_{e,t} = \max \left(1, \left\lceil \text{base\_lead\_time}_e \times \text{lead\_time\_multiplier}_{e,t} \right\rceil \right)
$$

$$
\text{unit\_cost}_{e,t} = \text{base\_unit\_cost}_e \times \text{cost\_multiplier}_{e,t}
$$

The base graph must never be mutated.

## 5.5 Daily state

At day $t$:

$$
S_t = (G_t, I_t, B_t, H_t, D_t, Z_t, C_t)
$$

where:

- $G_t$: current operational network;
- $I_t$: inventory by node and product;
- $B_t$: backlog by destination and product;
- $H_t$: shipments and their positions;
- $D_t$: demand realized on day $t$;
- $Z_t$: disruptions physically active on day $t$;
- $C_t$: accumulated costs and service counters.
The code representation is `SimulationState`.

Policies never receive `SimulationState` directly.

## 5.6 Transition

$$
S_{t+1} = T(S_t, A_t, w_t)
$$

where:

- $T$ is shared deterministic simulation logic;
- $A_t$ is the validated executed action set;
- $w_t$ is the policy-independent exogenous event set;
- $S_{t+1}$ is the next state.

Given identical inputs, the transition must produce identical outputs.

## 5.7 Cost objective

For one run:

$$
J = C_{\text{transport}} + C_{\text{reroute}} + C_{\text{expedite}} + C_{\text{holding}} + C_{\text{backlog}} + C_{\text{late}} + C_{\text{terminal}}
$$

$C_{\text{terminal}}$ is zero when the drain phase clears all shipments and backlog. It is used only if unresolved state remains at the configured maximum drain day.

## 5.8 Paired disruption metric

For policy $p$, scenario $s$, and replication $r$:

$$
\text{TCD}_{p,s,r} = J^{\text{disrupted}}_{p,s,r} - J^{\text{undisrupted}}_{p,s,r}
$$

The policy comparison is:

$$
\Delta_{s,r} = \text{TCD}_{\text{LLM},s,r} - \text{TCD}_{\text{heuristic},s,r}
$$

Interpretation:

- $\Delta < 0$: LLM lower disruption cost;
- $\Delta > 0$: heuristic lower disruption cost;
- $\Delta = 0$: equal disruption cost.

## 6. Global conventions

### 6.1 Time

- Time is an integer number of days.
- Day `0` is the loaded initial state.
- Warm-up days are `1` through `warmup_days`.
- The evaluation phase begins on `warmup_days + 1`.
- `horizon_days` is the final day on which normal demand and shipment releases occur.
- The optional drain phase follows the horizon.
- Shock start and end days are inclusive.
- A shock ending on day `27` is removed at the start of day `28`.

### 6.2 Quantities

- Product, inventory, demand, shipment, and capacity quantities are integers.
- Shipment splitting is forbidden.
- Every shipment quantity must fit the static capacity of every edge in its configured initial route.
- Costs are Python `float` values and are rounded only when written for display.
- Internal cost calculations retain full floating-point precision.
- CSV and JSON cost outputs use six decimal places.

### 6.3 Currency and units

Version 1 uses configuration labels rather than hard-coded assumptions:

```text
quantity_unit: units
distance_unit: km
time_unit: day
currency: EUR
```

All values in one experiment must use the same units.

### 6.4 Identifiers

Identifiers must:

- be non-empty strings;
- contain only lowercase letters, digits, and underscores;
- remain stable across runs;
- be unique within their entity type.

Generated shipment identifiers use:

```text
shipment_<release_day:03d>_<sequence:03d>
```

Example:

```text
shipment_021_001
```

Generated route identifiers are the edge identifiers joined by `__`.

### 6.5 Ordering

Whenever order can affect results, use an explicit deterministic sort.

Shipment allocation order:

1. earliest due day;
2. earliest release day;
3. lexicographically smallest shipment ID.

Route tie-breaking order:

1. lowest estimated total cost;
2. earliest estimated arrival day;
3. fewest edges;
4. lexicographically smallest route ID.

Dictionary iteration order must never be relied upon for scientific behavior.

### 6.6 Numerical comparisons

Use:

```python
COST_TOLERANCE = 1e-9
OUTPUT_TIE_TOLERANCE = 0.01
```

- Algorithmic cost equality uses `1e-9`.
- Policy result ties use one currency cent.

## 11.7 `simulation/costs.py`

Owns shared cost calculations.

Required functions:

```python
charge_edge_entry_transport_cost(...)
charge_reroute_cost(...)
charge_expedite_cost(...)
charge_end_of_day_holding_cost(...)
charge_end_of_day_backlog_cost(...)
charge_delivery_late_penalty(...)
charge_terminal_cost(...)
total_cost(...)
```

Exact rules:

### Transport

When a shipment enters an edge:

$$
\text{cost} = \text{quantity} \times \text{effective\_unit\_transport\_cost}
$$

Charge once per edge entry.

### Reroute

When a validated `REROUTE` changes the remaining route:

$$
\text{cost} = \text{quantity} \times \text{reroute\_cost\_per\_unit}
$$

Charge on every executed reroute.

### Expedite

When a validated `EXPEDITE` changes the remaining route:

$$
\text{cost} = \text{quantity} \times \text{expedite\_premium\_per\_unit}
$$

Emergency-edge transport cost is still charged normally at edge entry.

### Holding

At the end of each day:

$$
C_{\text{holding},t} = \sum_{v,p} \text{inventory}_t(v,p) \times \text{holding\_cost}_p
$$

### Backlog

At the end of each day:

$$
C_{\text{backlog},t} = \sum_{v,p} \text{backlog}_t(v,p) \times \text{backlog\_cost}_p
$$

### Late delivery

When a shipment reaches its final destination:

$$
\text{lateness} = \max(0, \text{delivered\_day} - \text{due\_day})
$$

$$
\text{late\_cost} = \text{quantity} \times \text{lateness} \times \text{late\_penalty}_p
$$

Charge once.

### Terminal

At the last drain day, if unresolved state remains:

$$
\text{terminal\_backlog} = \text{remaining\_backlog} \times \text{backlog\_cost\_per\_unit\_day} \times \text{terminal\_penalty\_days}
$$

For each undelivered shipment:

$$
\text{terminal\_shipment} = \text{quantity} \times \text{late\_penalty\_per\_unit\_day} \times \max(1, \text{last\_day} - \text{due\_day})
$$

The baseline uses `terminal_penalty_days=30`.

## 11.13 `policies/heuristic.py`

Owns the classical benchmark.

It must be deterministic.

The exact algorithm is:

1. Construct a `WAIT` candidate from `current_plan`.
2. Construct one candidate for every non-emergency route as `REROUTE`.
3. Construct one candidate for every emergency route as `EXPEDITE`.
4. Remove `EXPEDITE` candidates unless:
   - predicted lateness under `WAIT` is at least `expedite_trigger_lateness_days`; or
   - there is no non-emergency route.
5. Compare `estimated_total_cost`.
6. Choose the lowest-cost candidate.
7. Apply tie-breaking preference:
   - `WAIT`;
   - `REROUTE`;
   - `EXPEDITE`;
   - route ID.
8. Return the structured action.

If no route exists, return `WAIT`.

The heuristic must not use hidden future events.

## 11.17 `experiments/event_tape.py`

Replication seed:

\[

\]

```text

```

Use the first eight bytes as an unsigned integer.

Required streams:

```text

```

Draw order within a stream is deterministic:

- days ascending;
- destination IDs ascending;
- product IDs ascending;
- edge IDs ascending.

```python
round(random.gauss(mean, standard_deviation))
```

Then clamp to configured minimum and maximum.

```text
0 days when random draw <= reliability
1 day otherwise
```

Generate a delay draw for every edge and every day, regardless of whether a policy uses that edge. This prevents policy choices from changing the random-number sequence.


For every replication:

## 13. Day-0 initial state and warm-up

### 13.1 Day 0

At day 0:

- the base network is normal;
- all operational states use defaults;
- plant inventory is 200;
- backlog is zero;
- there are no shipments;
- costs and service counters are zero;
- no shock is active or known.

### 13.2 Warm-up

Warm-up runs days 1 through 20.

Rules:

- use the undisrupted event tape;
- decisions are disabled;
- shipments follow their configured route;
- ordinary delays and capacity constraints still apply;
- demand and replenishment occur normally;
- no designed shock is active;
- the purpose is to build a realistic in-transit pipeline.

At the end of day 20:

- clone the complete physical state;
- preserve inventory, backlog, shipments, due dates, and positions;
- preserve no active designed shock;
- record pre-shock inventory and backlog;
- reset all cost and service counters to zero;
- reset daily capacity counters;
- retain the current day as 20.

This reset means evaluation costs start on day 21.

## 14. Exact daily event order

For each day \(t\) after the current state:

1. **Begin day**
   - set `state.day=t`;
   - reset daily edge and node usage.

2. **Reveal information**
   - add shocks whose `information_day=t` to known shocks.

3. **Apply physical shocks**
   - rebuild operational multipliers and availability from all shocks active on day \(t\);
   - do not incrementally mutate stale multipliers.

4. **Process arrivals**
   - find in-transit shipments with `edge_arrival_day=t`;
   - process in deterministic shipment order;
   - if destination node is unavailable, postpone arrival to `t+1`;
   - if destination storage would overflow, postpone arrival to `t+1`;
   - otherwise place shipment at the destination node;
   - if this is the final destination:
     - mark delivered;
     - add quantity to inventory;
     - charge late-delivery penalty;
   - otherwise mark `AT_NODE`.

5. **Release scheduled shipments**
   - create release events for day \(t\);
   - validate source availability, source capacity, and source storage;
   - baseline configuration guarantees feasibility;
   - a violated guarantee raises `SimulationInvariantError`;
   - released shipments are `AT_NODE` at the source.

6. **Realize and fulfil demand**
   - add the day demand to total demand counters;
   - use inventory first to clear existing backlog;
   - then use remaining inventory for same-day demand;
   - unmet same-day demand becomes backlog;
   - inventory and backlog remain non-negative.

7. **Build decision set**
   - consider every non-delivered shipment at a node;
   - build all observations from this same pre-action state;
   - do not execute an earlier action before building a later observation.

8. **Request policy decisions**
   - process observations in deterministic shipment order;
   - measure policy decision latency;
   - collect proposed actions.

9. **Validate and resolve fallback**
   - validate each proposed action;
   - process abstentions and invalid actions through configured fallback;
   - validate fallback;
   - use terminal `WAIT` if fallback is invalid;
   - record proposed, validation, fallback, and final action separately.

10. **Apply valid route changes**
    - apply `REROUTE` or `EXPEDITE`;
    - charge action cost;
    - update counters;
    - `WAIT` leaves the route unchanged.

11. **Allocate departures**
    - include all shipments at nodes that have a next edge;
    - process in deterministic shipment order;
    - enforce current node processing and edge entry capacities;
    - if capacity is insufficient, shipment remains at node and `capacity_wait_days += 1`;
    - if dispatched:
      - reset `capacity_wait_days=0`;
      - charge transport cost;
      - sample no randomness here;
      - read the pre-generated edge delay for edge and day;
      - calculate arrival day;
      - mark in transit;
      - update daily used capacities.

12. **Charge end-of-day costs**
    - holding cost on inventory;
    - backlog cost on remaining backlog.

13. **Record metrics and assert invariants**
    - record daily metrics;
    - validate non-negativity, shipment-state consistency, and capacity limits;
    - fail immediately on violation.

### 14.1 Edge arrival day

If a shipment enters an edge on day $t$:

$$
\text{arrival\_day} = t + \text{effective\_lead\_time} + \text{ordinary\_extra\_delay}
$$

It may not arrive on the same day it enters an edge.

### 14.2 Multi-edge movement

A shipment arriving at an intermediate node during step 4 may enter its next edge during step 11 of the same day.

## 15. Shipment lifecycle

Valid state transitions:

```text
AT_NODE → IN_TRANSIT
IN_TRANSIT → AT_NODE
IN_TRANSIT → DELIVERED
AT_NODE → AT_NODE
```

`AT_NODE → AT_NODE` occurs when:

- waiting by policy;
- waiting for capacity;
- current node is unavailable;
- the next edge is unavailable;
- no route exists.

A delivered shipment never moves again.

### 15.1 Remaining route

`planned_route_edge_ids` always begins conceptually at the shipment origin, but `next_edge_index` identifies the next edge to execute.

A reroute replaces only the remaining segment:

```text
completed history remains unchanged
new remaining route begins at current_node_id
new remaining route ends at destination_node_id
next_edge_index resets to 0 for the replacement tuple
```

To avoid ambiguous indexing, after a reroute `planned_route_edge_ids` becomes only the new remaining route, and `next_edge_index=0`. Completed route history is retained only in decision/audit traces, not in the active route tuple.

### 15.2 Storage occupancy

Node occupied quantity is:

```text
inventory stored at node
+ quantities of non-delivered shipments currently AT_NODE
```

A shipment in transit does not occupy node storage.

The final plant inventory includes delivered shipment quantity.

## 16. Demand and backlog semantics

Version 1 has one product and one demand destination.

Daily fulfilment order:

1. oldest aggregate backlog;
2. current-day demand.

Backlog is aggregated by destination and product. Version 1 does not track individual customer orders.

Backlog-unit-days are the sum of end-of-day backlog quantities over evaluation and drain days.

No demand is generated after `horizon_days`.

---

## 17. Shipment release semantics

The replenishment plan releases one shipment every day from day 1 through day 60 inclusive.

Each shipment:

- contains 40 units;
- begins at `supplier_1`;
- ends at `plant_1`;
- uses the primary route;
- has due day `release_day + 15`.

No new shipment is released during the drain phase.

The policy cannot cancel, duplicate, resize, or create a shipment.

## 18. Shock semantics

### 18.1 Information and physical effects

`information_day` controls what policies know.

`physical_start_day` and `physical_end_day` control the network.

Version 1 baseline uses:

```text
information_day = physical_start_day
```

The full end date and operational effect are known when revealed.

### 18.2 Supported effects

#### Node closure

- node unavailable;
- no arrivals complete;
- no departures;
- adjacent edges not available for new route candidates.

#### Edge closure

- no new entries;
- shipments already in transit continue using their existing arrival day.

#### Node capacity reduction

- multiply daily departure processing capacity;
- node remains available.

#### Edge capacity reduction

- multiply edge entry capacity;
- in-transit shipments unaffected.

#### Edge lead-time increase

- applies only to shipments entering while active;
- in-transit shipments unaffected.

#### Edge cost increase

- applies only to edge entries while active.

### 18.3 Overlapping shocks

Overlapping effects combine as follows:

- availability is logical AND;
- capacity multipliers are multiplied;
- lead-time multipliers are multiplied;
- cost multipliers are multiplied.

All active shocks are applied from the immutable base values every day. Never multiply yesterday's already modified value.

## 19. Decision-trigger rules

A shipment requires a policy decision only when all are true:

- status is `AT_NODE`;
- current node is not the final destination;
- at least one trigger below holds.

Triggers:

1. a known active shock affects the current remaining route;
2. the next edge or next node is currently unavailable;
3. estimated arrival under the current route is after the due day;
4. `capacity_wait_days >= 2`;
5. the active route is malformed or no longer continuous.

If no trigger holds, the shipment continues automatically on its route.

A shipment may require decisions on multiple days.

No decision is made while a shipment is in transit.

## 20. Observation and information fairness

Every policy receives the same `DecisionObservation`.

The heuristic receives it as a Python object.

The LLM accesses only that object's fields through the prompt and tools.

The LLM does not receive:

- future random demand;
- future ordinary delays;
- hidden policy outcomes;
- another policy's decisions;
- final costs;
- mutable state;
- raw event tape;
- secrets.

Known disruption information is identical.

Route and cost estimators are shared.

The LLM may use more reasoning steps, but it may not access more underlying information.

## 21. Route feasibility and execution

A candidate route is structurally feasible when:

- it begins at the shipment's current node;
- it ends at the shipment destination;
- it is a simple path;
- it contains at most six edges;
- every node and edge is currently available;
- every edge effective daily capacity is at least the shipment quantity;
- every departure node effective processing capacity is at least the shipment quantity.

A route may still wait because several shipments compete for the same current-day capacity.

Route estimation does not reserve capacity.

### 21.1 Current plan and `WAIT`

The current plan may include a temporarily unavailable component.

For `WAIT`, estimated arrival uses the earliest known reopening day and normal effective lead times after reopening.

If no known reopening exists, estimated arrival and cost are `None`; `WAIT` remains executable but is treated as infinitely costly by the heuristic unless no alternative exists.

### 21.2 Reroute

A `REROUTE` route:

- must be one of the observation's approved options;
- must contain no emergency edge;
- replaces the remaining route;
- incurs reroute cost.

### 21.3 Expedite

An `EXPEDITE` route:

- must be one of the observation's approved options;
- must contain at least one emergency edge;
- replaces the remaining route;
- incurs expedite premium;
- also incurs all normal edge transport costs.

### 21.4 Abstain

`ABSTAIN` is never directly executed in the simulator.

It invokes fallback.

## 22. Classical heuristic details

### 22.1 Candidate scoring

For every candidate action:

$$
\text{estimated\_total\_cost} = \text{remaining\_transport\_cost} + \text{action\_cost} + \text{estimated\_late\_penalty}
$$

The heuristic does not estimate future holding or backlog costs.

This limitation is intentional and makes the benchmark transparent.

### 22.2 Candidate eligibility

- `WAIT` is always eligible.
- `REROUTE` requires a non-emergency route.
- `EXPEDITE` requires an emergency route and:
  - `WAIT` lateness at least 2 days; or
  - no non-emergency candidate.

### 22.3 Choice

Select the eligible candidate with minimum estimated total cost.

Exact ties prefer:

```text
WAIT
REROUTE
EXPEDITE
```

If route candidates tie, choose the lexicographically smallest route ID after the shared route sort.

### 23.3 Replay mode

## 24. Capacity allocation

### 24.1 Edge capacity

Edge capacity counts quantity entering the edge that day.

It does not count shipments already in transit.

### 24.2 Node processing capacity

Node processing capacity counts quantity departing the node that day.

### 24.3 Allocation

For each ready shipment in deterministic order:

- check node remaining processing;
- check edge remaining capacity;
- dispatch only if both can hold the entire shipment;
- never partially dispatch;
- otherwise leave shipment at node.

The baseline shipment quantity is 40, ensuring the alternative and emergency routes can carry one complete shipment.

## 25. Drain phase and terminal handling

After day 60:

- demand is zero;
- no new shipments are released;
- ordinary delay tape remains available;
- policies continue making decisions;
- costs continue accruing;
- the simulator stops early when:
  - all shipments are delivered; and
  - backlog is zero.

Maximum drain ends on day 90.

If unresolved:

- apply terminal cost;
- record unresolved quantities;
- set `terminated_with_unresolved_state=true`;
- still return a result rather than silently discarding the replication.
